# Implementation Plan: CLI-Based Agentic AI Harness (Ralph Wiggum Technique)

## Project Overview

This project is a CLI-based harness for autonomous coding agents inspired by the **Ralph Wiggum technique**. The core idea is to wrap a coding AI in a structured loop that enforces **memory, task decomposition, and iterative development**, allowing it to work on long-running projects without losing context. Instead of giving an agent one giant goal (e.g. *“build a web app”*), we use a harness with two specialized agents and persistent artifacts  (files, Git history) to guide progress across multiple sessions. This approach addresses common failure modes identified by Anthropic –  such as the agent trying to do too much at once, declaring completion  prematurely, or testing superficially – by providing external structure and accountability. The harness will  ensure the AI behaves more like a disciplined engineer than an  autocomplete, making consistent incremental progress with proper  record-keeping and validation.

**How It Works:** On first run, an **Initialization Agent** sets up the project environment and creates a **Product Requirements Document (PRD)** listing all required features as failing tests. Subsequently, a **Coding Agent** runs in a loop, picking one feature at a time from the PRD to implement and test, then marking it as completed. Each coding session starts  fresh (empty AI context) but leverages the persisted files (codebase,  PRD, logs, Git commit history) as “memory” to know what’s done and  what’s next. By reading these  artifacts at startup, the agent can resume work without forgetting  previous progress. This harness operates entirely on the local machine  (no cloud runtime) and uses the **OpenAI Agent SDK (TypeScript)** to manage agent reasoning and tool use. Key tools include **Playwright** for automated end-to-end testing of features and **ESLint** for code quality enforcement.

## Agents and Workflow

### Initialization Agent

The **Initialization Agent** runs **once** at the beginning of a new project (or when the harness is invoked on a  fresh project spec). Its role is to lay a strong foundation for all  future coding sessions. The Initialization Agent will perform the  following tasks in sequence:

- **Read Project Spec & Plan Features:** It loads the predefined project specification (e.g. from a file `project_spec.md` or similar) that describes the application to build. Using this, the  agent generates a comprehensive list of product requirements (features)  needed to fulfill the spec. Each requirement will include a clear **description** and may include **acceptance criteria or test steps**. For example, if the spec says "support user login", the agent might break this into features like *“Users can register with email and password”*, *“Users can log in with valid credentials”*, etc., each with step-by-step success criteria. All features are initially marked as not implemented (fails) in the PRD.
- **Produce PRD as JSON:** The agent outputs the feature list as a JSON file (e.g. `prd.json`). Each entry in this JSON represents a requirement with fields such as `description` (what the feature is), possibly `steps` (detailed acceptance test steps), a `category` or type, and a `passes` flag set to **false** initially. This file serves as a persistent **to-do list** for the Coding Agent. Using JSON (instead of free-form text) is  deliberate – it reduces the chance of the AI inadvertently altering the  structure or content, aside from the `passes` field.
- **Setup Project Scaffolding:** Based on the project spec and intended tech stack, the Initialization  Agent creates the initial project structure and configuration. This  includes generating source code directories, config files, and choosing  frameworks or libraries if the spec implies them. For example, if the  spec is for a web app, it may create a basic Bun TypeScript project  structure (with perhaps an `src` directory, a package manifest, etc.), or scaffold a simple web server  or UI framework as appropriate. It will also generate baseline files  like `playwright.config.ts` for testing and an `.eslintrc.js` for linting rules.
- **Generate Startup/Shutdown Scripts:** If the project needs to run a local server or background process for  testing (for instance, a web service that Playwright will hit), the  agent creates a `startup.sh` script to launch the app (e.g. start a dev server or any required services) and a `shutdown.sh` to cleanly stop them. These scripts ensure that automated tests can  start the environment and later tear it down. They might not be needed  for every project (e.g. a purely static codebase), so the agent will  create them only if the spec’s tech stack demands (conditional on  project type).
- **Initialize Git Repository:** The agent runs a `git init` in the project directory to start version control. All initial files  (scaffolding code, PRD JSON, scripts, config files, etc.) are added and  an initial commit is made (e.g. commit message “Initial project  scaffolding and PRD”). This ensures there is a commit history from the  very start.
- **Record Progress Log:** Optionally, the Initialization Agent may create a progress log file (e.g. `progress.md` or `progress.txt`) summarizing what it did. This log serves as a **session handoff** note for subsequent agents. For example, it might list “Set up project structure, created 15  feature entries in prd.json, initialized git, ready for coding phase.”  The presence of both a progress log and the git commit history will  later help coding agents quickly get up to speed on the project state.
- **Handoff to Coding Agent:** After setting up everything, the Initialization Agent triggers the next phase. It can either exit and allow the CLI to invoke the Coding Agent, or if using the OpenAI Agent SDK’s multi-agent capabilities, it can  perform a **handoff** to the Coding Agent within the same run. In our harness, we’ll likely just end the init phase and then launch  the coding loop as a separate process or function call. The key point is that after initialization, the environment is ready and all features  are known (but unimplemented), so the Coding Agent can start picking  them off one by one.

**Why these steps?** This structured initialization ensures the project doesn’t start from a blank slate in each session. By pre-defining the full scope of work  (feature list) and setting up infrastructure, we prevent the AI from  trying to “one-shot” the whole app or skipping important steps. It addresses the failure mode of *“doing too much at once”* by forcing a detailed breakdown, and *“declaring victory early”* by explicitly listing all required features as unfinished. The initial commit and progress log also address the *memory gap* between sessions: future agents can read what’s been done via these artifacts, rather than guessing or repeating work.

### Coding Agent

The **Coding Agent** is responsible for iteratively implementing the features from the PRD,  one at a time, in subsequent sessions. It runs in a loop (potentially  across multiple CLI invocations or a long-running process) until all PRD items are marked as completed (`passes=true`). Each session of the Coding Agent will:

- **Check Time Budget:** The agent is configured to run for up to **4 hours 30 minutes** in a session. At the start of each iteration (each feature  implementation cycle), it checks how much time has elapsed. If the  session is nearing its cap (e.g. only a few minutes remaining), the  agent will refrain from starting a new feature to avoid half-implemented work. Instead, it will clean up and end the session gracefully,  allowing a fresh run later to continue. (In practice, this could be  implemented by tracking the start time and breaking out of the loop when time > 4h25m or so.)
- **Select Next Feature (from PRD):** The agent loads `prd.json` and scans for the first feature entry where `"passes": false`. This represents the highest-priority incomplete feature. (Features  could be sorted by priority or order in the PRD. The Initialization  Agent might have ordered them logically.) That feature becomes the **task for the current iteration**. The agent will **not** modify the PRD content except to update the status after  implementation. It strictly avoids adding/removing features or altering  descriptions – its mandate is only to change `passes` to true when a feature is done, as a guard against scope creep or cheating tests.
- **Orient Phase (Read Context):** Before coding, the agent orients itself by examining the project state. It will read the **Git history** (e.g. recent commit messages, `git log` or diff) and the **progress log** (if one exists) to understand what has been done in prior sessions. This is analogous to a human engineer reading documentation or last  day’s notes when coming back to a project. By doing so, the agent avoids duplicating work or reintroducing bugs, and it knows the current  baseline. For example, the git log might show “Added user authentication module” in the last commit, so the agent knows that part is completed.  This orientation step leverages the persistent memory artifacts we set  up, solving the context window limitation by explicitly feeding relevant history on each run.
- **Implement Phase (Coding the Feature):** The agent proceeds to implement the selected feature in the codebase. It writes **human-maintainable, modular TypeScript code** to fulfill the requirement. Following best practices, it will use an **object-oriented** or well-structured approach as appropriate, integrating with existing  code. The agent is guided by the acceptance criteria defined in the PRD  for that feature, and by general coding standards (reinforced by  ESLint). It should also update or create any necessary documentation,  configuration, or test stubs related to the feature. During this phase,  the agent might make multiple tool calls or reasoning steps: e.g., using the OpenAI functions or tools if available (like searching docs,  reading files, etc.), though in our local harness most context is on  disk. The key is **incremental progress** – the agent handles *only one feature at a time*, which is critical to prevent the “too much at once” pitfall. By focusing narrowly, it increases the chances of successfully completing the feature within the available context and time.
- **Test Phase (Validate Feature):** Once the code for the feature is written, the agent must verify it  works and meets the acceptance criteria. This is done by running  automated tests using **Playwright**. There are a couple of strategies here:
  - Ideally, each feature in the PRD includes a list of **steps** (user actions and expected outcomes). The agent can translate these steps into a Playwright test script (or  use a pre-generated test if one exists). For example, if the feature is *“New chat button creates a fresh conversation”*, the steps might be: *open the app, click 'New Chat', verify a new conversation appears*. The agent either writes a Playwright test case on the fly or uses a  template in the repo to perform these actions in a headless browser and  assert the expected outcome.
  - If this is the first time the  feature’s test is run, it will likely fail until the implementation is  correct. The agent should debug any failing steps: examine errors or  browser logs, fix the code accordingly, and rerun the test until it  passes. This may involve a few cycles of refine-and-test internally  within the Implement/Test phase.
  - In addition to the feature’s own test, the agent will perform **one spot-check test on another core feature** of the app to guard against regressions or superficial testing. For  example, after implementing the “New chat” feature, it might also run a  quick sanity test like *“Existing features still load the main page”* or some other test from a different area of the app. This extra step  helps catch if a new change unintentionally broke something else,  addressing the “superficial testing” problem.
  - All tests are run via Playwright  in an automated way (likely via a script or Node API). The harness  ensures the app is running (using `startup.sh` if needed) before tests, and stops it afterwards using `shutdown.sh`.
- **Commit Changes:** Once the feature’s implementation passes its tests, the Coding Agent prepares a git commit. The agent creates a **descriptive commit message** explaining the change (e.g. “Implement Feature: New Chat button  functionality, with tests”). It then stages the modified files (source  code, possibly new tests, updated `prd.json`, etc.) and commits. Each commit serves as a checkpoint and documentation of progress. The commit message and diff will later help future sessions see what was done.
- **Update PRD:** The agent updates the `prd.json` file to mark the implemented feature’s `"passes"` field to **true**. This indicates that the feature is completed and its tests pass. The agent does **not** remove the feature from the list; it simply toggles the status. This  way, the PRD remains an authoritative ledger of all features and their  status (similar to a to-do list with checked items).
- **Log Progress:** As with the initialization step, the Coding Agent can append an entry to `progress.md` (if using one) summarizing this session’s accomplishments: e.g.  “Completed feature X, tests pass. Next planned feature: Y.” This is  useful for human developers to read, and for the next AI session to  quickly recap what has just been done. Even if no separate progress file is used, the **PRD and Git commit** together act as the state record for the next run.
- **Loop Continuation:** The agent then loops back to select the next unfinished feature from `prd.json`. This loop continues until the agent’s time budget is exhausted or until there are no remaining `passes=false` items (meaning the project is fully implemented). If time runs out  mid-project, the harness simply stops; it can be re-invoked to continue  where it left off, thanks to the persisted state. If all features are  done, the harness can terminate with a success message.

**OpenAI Agent SDK Usage:** We will implement the Coding Agent using the OpenAI Agent SDK’s  TypeScript API. This SDK supports running an agent in a loop with tool  usage, and crucially it has the concept of **Handoffs** (agents delegating tasks to other agents or new instances), which fits our two-agent pattern. The Coding Agent can be defined as an `Agent` with access to tools like file I/O (to read/write code and PRD), a  shell tool (to run tests, git commands, etc.), and maybe a text editor  tool if needed. The agent’s prompt/instructions will encode the above  workflow: it will be instructed to take one feature from the PRD,  implement it, run tests, and so on, without deviating. We will utilize  the SDK’s built-in loop mechanism so that the agent can call tools (like executing `npm test` or `bun run tests`) and react to the results, continuing reasoning until the feature is done. The **multi-session** continuity is achieved not through the model’s memory, but through reading/writing files and using Git as described.

This design ensures the agent  works methodically through the feature list, maintaining a clean project state after each session (no half-done features, all tests passing,  code linted). By committing after each feature and not carrying over  hidden state, we allow even a brand new agent instance (fresh context)  to pick up where the last left off. In essence, we are leveraging source control and artifact files as the  “extended memory” of the AI, which is the key insight behind effective  long-running agent harnesses.

## Technical Stack and Requirements

Our implementation will use the following technologies and tools:

- **Bun Runtime (JavaScript/TypeScript)**: Bun will be the runtime environment to execute our CLI tool. Bun’s fast startup and native TypeScript support make it ideal for a local  development CLI. We will write our code in TypeScript and run it with  Bun, taking advantage of its performance and built-in utilities (like  bundling and running TS without separate compilation).
- **TypeScript Language**: All code (the harness and the generated project code) will be in  TypeScript. This ensures type safety and maintainability for the  generated project. The agents will also generate TypeScript code for the project they are building. We’ll set up tsconfig and module resolution  appropriate for Bun.
- **OpenAI Agent SDK (TypeScript)**: We will use OpenAI’s Agents SDK for JavaScript/TypeScript (e.g. the `@openai/agents` npm package) to implement the agent logic. This SDK provides  abstractions for defining agents with instructions, tools, and looping  behaviors. It supports **agent loops**, tool invocation, and **multi-agent coordination** (via handoffs) out of the box. By using this SDK, we can focus on our agent’s high-level logic while  relying on the SDK for robust tool interfacing and context management.  (Note: This is *not* the older OpenAI ChatCompletion API; it’s a higher-level framework specifically for building agentic systems in TS.)
- **Playwright (for Testing)**: Playwright will be used to automate browser interactions for end-to-end testing of the application. It can simulate user actions in a headless  browser and verify UI or API outputs. We’ll install Playwright and set  up a `playwright.config.ts` suited for our project (e.g. using Chromium, possibly configuring base  URL or server startup fixtures). The Coding Agent will use Playwright in the Test Phase to ensure each feature works as intended. This might  involve the agent calling Playwright’s test runner via CLI (`npx playwright test`) or using a programmatic API to run specific tests.
- **ESLint (for Linting)**: ESLint is integrated to enforce coding standards. An ESLint config (likely `.eslintrc.js` with recommended rules or a standard style guide) will be part of the  project scaffold. The agent should run ESLint (or at least ensure no  lint errors) after implementing a feature, to keep code quality high.  This can be automated as a tool call (e.g. using `npm run lint` if configured). Linting ensures the AI writes clean, consistent code  and catches any obvious issues (unused variables, etc.) as part of the  harness’s definition of “done” for a feature.
- **Local Development (No Cloud Infra)**: The harness is intended for local use only. All operations occur on the developer’s machine: reading/writing the local filesystem, running  local browsers for tests, and using the local git repository. The OpenAI API calls (through the Agent SDK) are the only cloud interaction (to  OpenAI’s servers for the model inference). There is no need for setting  up servers, databases, or cloud services for the harness itself. This  makes the tool lightweight and easy to run in any development  environment. (It’s essentially an advanced CLI program managing AI  interactions and local dev tools.)
- **Git**: While not a separate technology requirement, Git is a crucial part of the process. We assume the developer has `git` installed locally. The harness will invoke git commands (init, add,  commit, etc.) via shell. Git serves both as a version control for the  evolving project and as a mechanism of preserving state and progress  across AI sessions.

In summary, the stack leverages  Bun + TS for implementation, OpenAI’s agent capabilities for  intelligence, and Playwright/ESLint to ensure the output (the software  being built) is robust. The selection of these tools is aligned with the goal: **fully automated, high-quality code generation with iterative validation**. For instance, if the agent writes code that breaks a lint rule or a  test, those tools will flag it, and the agent can correct the issue  before considering the feature done. This results in a much cleaner  final codebase (no accumulated errors), akin to how a human developer  would use tests and linters to catch mistakes early.

## File Structure and Deliverables

The following files constitute  the deliverables of the project harness. They outline both the harness  implementation itself and the artifacts it manages in each run:

- **`ralph.ts`** – The entry-point CLI script. This is the main program that the user will run (e.g. `bun run ralph.ts`). It parses command-line arguments and orchestrates the two-agent workflow. On invocation, `ralph.ts` will determine whether to initialize a new project or continue an existing one:

  - If the current directory (or  specified project directory) does not have an initialized project (no  PRD or git), it will run the Initialization Agent.
  - If a PRD and repo already exist, it will skip init and proceed to launch the Coding Agent loop.
  - It may accept flags like `--spec path/to/spec.md` or `--continue` to explicitly control behavior.
  - This script handles setting up  any necessary global configurations (like reading an API key for OpenAI  from env), and catching any errors to output to the user. Essentially, `ralph.ts` ties everything together.

- **`init-agent.ts`** – Module implementing the Initialization Agent’s logic. It defines the agent (likely by constructing an `Agent` instance from OpenAI SDK) with the specific system prompt/instructions  needed for initialization. It also implements the functions or tool  calls required (e.g. file write operations to create the PRD and  scaffold files, executing `git init`). This file may export a function like `runInitialization(specPath: string)` that `ralph.ts` can call. It will produce the `prd.json` and initial project files as described in the Initialization Agent  section. After execution, it returns or signals that initialization is  complete.

- **`coding-agent.ts`** – Module implementing the Coding Agent’s logic. It defines the  continuous loop that picks features and executes the Orient → Implement → Test → Commit cycle. Using the OpenAI Agent SDK, it may break the work  into smaller tool calls and reasoning steps. This file could contain the main loop that runs until time/feature conditions are met, as well as  helper functions (e.g. to run tests, update files, commit to git). It  might export `runCodingLoop()` which `ralph.ts` invokes after initialization. It also contains the prompt templates or instructions for the Coding Agent, enforcing rules like *“do not change PRD except passes”* and *“one feature at a time”*.

- **`startup.sh`** – A shell script to start the application (if applicable). For example, if the project is a web server, running this might start the server on a local port. The Initialization Agent will create this if the project  spec implies a runnable app. It might contain commands like `bun run src/index.ts` or `bun dev` etc., depending on how the project is set up. The harness can use this  script to ensure the app is running before Playwright tests. If the  project doesn’t need a runtime server (maybe it’s a library or a purely  algorithmic project), this file could be omitted or just left trivial.  (The plan allows conditional creation as needed.)

- **`shutdown.sh`** – A counterpart to `startup.sh` that stops the application. This could kill any background process started by startup (for instance, `kill $(lsof -ti :3000)` to kill a server on port 3000, or a more graceful termination if we  track the process ID). This ensures a clean teardown of the environment  after tests. Again, this is created if needed; for many simple projects, it might not be strictly required, but including it adds robustness to  the test automation.

- **`prd.json`** – The Product Requirements Document in JSON format, generated by the  Initialization Agent. This is a key artifact that lists all features and their status. The structure might be an array of objects like:

  ```
  [
    {
      "category": "functional",
      "description": "New chat button creates a fresh conversation",
      "steps": [
        "Navigate to main interface",
        "Click the 'New Chat' button",
        "Verify a new conversation is created and appears in sidebar"
      ],
      "passes": false
    },
    { ... next feature ... }
  ]
  ```

  Each feature’s `steps` define an acceptance test which the Coding Agent will execute with Playwright. Initially, all `passes` are false. The Coding Agent updates this file, marking features true as it completes them. This file persists across runs, so if the process is restarted, it knows what’s done. It effectively serves as both a **to-do list** and a **test checklist**.

- **`playwright.config.ts`** – Configuration for Playwright tests. This likely includes setting the  test directory, test runner options, maybe a base URL or fixture to run  the `startup.sh` before tests. For example, we might configure a global setup that runs `startup.sh` to launch the app, and a global teardown that runs `shutdown.sh` after tests. It might also configure reporters or timeouts appropriate  for our environment. The Initialization Agent can generate this file  with sensible defaults (like using Chromium browser, and expecting tests in a `tests` folder).

- **`.eslintrc.js`** – ESLint configuration file for the project. The Initialization Agent  will output this, possibly extending a popular style guide (like Airbnb  or Google) or using TypeScript recommended rules. This ensures the  agent’s generated code follows a consistent style. The Coding Agent can  run `eslint . --max-warnings=0` (for example) as part of its testing phase to catch any violations.  Keeping the lint config in a file allows easy customization and is  familiar to developers.

- **Additional Files**: The harness will also create other standard project files as needed: e.g. a `package.json` or Bun’s equivalent (perhaps Bun uses `bun.toml` or still `package.json` for dependencies – we will include whatever is needed to manage  dependencies like Playwright and ESLint in the project). It may also  produce stub files for the app (like an entry point `src/index.ts`) and possibly a README for the project. These are implied by the spec  and tech stack choices and will be handled by the Initialization Agent.

All the above deliverables (except `ralph.ts`, `init-agent.ts`, `coding-agent.ts` which are part of the harness itself) will reside in the project working directory and be tracked in git. The harness code (`ralph.ts` etc.) could be used globally or per project; typically one would keep  the harness separate from the project repo, but it’s possible to include it as dev dependency. In any case, our plan focuses on producing these  outputs in a consistent way.

## Implementation Phases

To build this harness in a structured manner, we will proceed through several phases:

1. **Setup Environment & Dependencies**: Initialize a new Bun project to host the harness code. This involves creating a `package.json` (if needed) and installing required packages:

   - Install **OpenAI Agent SDK** (TypeScript) – e.g. `bun add @openai/agents` (assuming that is the package name).
   - Install **Playwright** – e.g. `bun add -d @playwright/test` (as a dev dependency, since it’s used for testing).
   - Install **ESLint** – e.g. `bun add -d eslint @typescript-eslint/parser @typescript-eslint/eslint-plugin`.
   - Optionally install any types or utils (e.g. `@types/node` if needed for Node.js types).
      Ensure that Bun’s toolchain can handle these (Bun uses NPM-compatible packages). After installing, configure **ESLint** (create an `.eslintrc.js` in the harness project to lint our harness code itself) and perhaps a basic `tsconfig.json` if Bun doesn’t auto-generate one. This phase sets up our development environment for building the harness.

2. **Implement CLI Entry Point (`ralph.ts`)**: Create the `ralph.ts` script with a clear CLI interface. Use Node’s `process.argv` or a library (maybe Bun has an argparse utility) to parse commands:

   - If the user runs `ralph init <spec_file> [project_dir]`, then call the Initialization Agent workflow. If just `ralph` or `ralph continue`, assume current directory and continue mode.

   - The CLI should handle checking if `prd.json` exists in the target directory. For instance:

     ```
     const hasPRD = fs.existsSync(path.join(projectDir, "prd.json"));
     if (!hasPRD) {
       runInitialization(specFilePath);
     }
     runCodingLoop();
     ```

   - If `spec_file` is required for init, validate its presence. Read the spec file content if needed (to provide it to the Initialization Agent).

   - The CLI might also accept a time limit parameter or other configurations (but we can start with defaults).

   - Initialize the OpenAI API key (e.g. from `OPENAI_API_KEY` env) so that the Agent SDK can use it. (The Agent SDK might allow setting a default API key globally – we will do that before running agents.)

   - This file mainly delegates to the appropriate agent logic and handles high-level errors (e.g. if an agent throws an exception, catch and log it). It could also handle  termination signals to ensure any child processes (like a dev server or  tests) are killed if the user aborts.

3. **Build Initialization Agent (`init-agent.ts`)**: Develop the Initialization Agent using the OpenAI Agent SDK:

   - **Agent Definition**: Configure an agent with a name (e.g. "InitializationAgent") and an instruction prompt that clearly states its duties: *“You are an Initialization Agent. Your goal is to set up a new project given the specification. Do not implement features; instead, list all  features in a PRD JSON file, scaffold the project structure, and prepare for coding. You have tools to write files, run shell commands, and  output JSON.”* Include the specifics: it must produce `prd.json` with all features (passes=false), create any necessary files (`startup.sh`, etc.), and initialize git. Emphasize it should commit the results and not proceed to coding itself.
   - **Tools**: Register tools for file system access: e.g. a **writeFile** tool (to create files with given content), a **shell** tool (to execute commands like `git init && git add . && git commit`), maybe a **readSpec** tool (to get the content of the project spec file). The OpenAI SDK  likely has some built-in file operations or we might implement custom  tools that the agent can call via function calls. The spec content can  be given either via the prompt (if small) or via a tool that reads the  spec file and returns its text to the agent (to avoid prompt size  issues).
   - **Process**: The agent will likely follow steps in its chain-of-thought. We might  not need to hardcode the sequence if we trust the AI, but to reduce  error, we can structure the prompt to break down tasks:
     1. Parse the spec and produce a list of features (maybe first output as a JSON array draft).
     2. Create project files (this could be done by directly instructing it to call file tools for each necessary file).
     3. Call git commands at the end.
   - To enforce the PRD format,  provide an example in the prompt or a schema. Possibly include the JSON  schema or a small example like one feature object.
   - After agent planning, capture its output or the results of its tool calls. For example, after it indicates the content of `prd.json`, actually write that file (if not done via tool calls automatically). Ensure all files are created as intended.
   - Run git initialization outside or via agent’s tool. We might do this outside the model for reliability: once we trust `prd.json` and other files are ready, our code (not the AI) could execute the git  commands. However, doing it through the AI’s plan (i.e., the agent says  “Initial commit done”) provides a traceable log. A hybrid approach might be safest: the agent decides what files to create and their content,  our harness code performs the actual FS writes and git commits according to the agent’s plan (this avoids the agent messing up Git state).
   - Finally, ensure that after this function, the `prd.json` exists and is well-formed, and initial commit is made. Then in `ralph.ts`, proceed to coding.

4. **Build Coding Agent (`coding-agent.ts`)**: This is the most complex part. We implement the continuous Coding Agent as per design:

   - **Agent Setup**: Define the agent’s instructions with strong constraints: *“Work on one feature at a time from the PRD. Only mark it as done when tests  pass. Do not change any other part of PRD. Keep code clean.”* Also include guidance like *“If nearing time limit (4.5h), finish up or exit.”* Since the agent runs continuously, we likely rely on an external loop  to enforce the time – but we can instruct the agent to be mindful of  time by providing current time or a timer tool.
   - **Tools for Coding Agent**:
     - File system tools: read files (to get context of codebase), write/append files (to implement feature code or tests).
     - Possibly a code editor tool if the SDK has one that can apply patch diffs to files.
     - Shell tools: e.g. a **runTests** tool that executes `npx playwright test` or runs a specific test file. Also a **runLint** tool for `eslint` checks.
     - Git tools: a **commit** tool for staging and committing files with a message.
     - Perhaps a **getGitDiff** tool: returns a summary of last commit or `git diff HEAD` to understand changes, and a **getProgressLog** to read `progress.md`.
     - Timer tool: if we can provide  current time or a way to check elapsed time, the agent can call it to  decide on stopping. Alternatively, our outer loop can break out without  the agent’s involvement.
   - **Orient Phase Implementation**: When starting (or on each loop), the agent should call a tool to **read the relevant context**:
     - e.g. use a **readFile** tool on `prd.json` to see all features and find the next `false`.
     - read the `progress.md` (if exists) to see what last happened.
     - maybe a custom tool `getGitLog` that returns the last N commit messages.
        Our harness can feed some of this context initially as part of the prompt to save steps (for instance, include the content of `prd.json` in the prompt input each time). The Anthropic approach favored reading a single progress file. We can simplify by feeding the model the PRD JSON and a short git summary at the start of each agent run via the `AgentOptions.context` if the SDK allows. Otherwise, the agent will explicitly call tools to get this info.
   - **Implement Phase Implementation**: The agent, once it has chosen a feature, will likely break the work  into code-writing steps. The OpenAI SDK might allow an agent to propose  code changes which we then apply. One strategy:
     - The agent can be prompted to  output a diff or code snippet for each file to change. Our harness can  then apply those changes to the filesystem.
     - Or we use a loop where the agent calls a tool like `editFile(filename, instructions)` repeatedly until it’s satisfied. (OpenAI’s functions can model something like this with iterative refinement.)
     - Simpler: The agent could just  output the full content of new/modified files. Our harness then writes  them. But for large projects that might be too heavy on context.
     - We can also integrate an approach where after writing, the agent can compile/run the project (if needed)  to verify nothing crashes.
     - ESLint can be run here via a  tool; if it returns errors, the agent should fix them (this can be part  of the loop until lint passes).
     - We instruct the agent to keep changes minimal and focused on the feature.
   - **Test Phase Implementation**: Expose a `runTests` tool. When invoked, our harness actually runs `startup.sh` (if exists) to launch the app, then runs Playwright tests. We can  narrow to the specific test scenario if we have that – e.g., generate a  Playwright test script on the fly for the current feature and run it, or run the whole test suite (which at early stages might just test that  one feature). Running the entire suite each time might be fine too, as  it ensures regression tests for previously done features. This will  return results (pass/fail). The agent sees the result:
     - If tests failed, the agent goes back to Implement steps: fix code or tests accordingly. This loop continues until `runTests` returns all clear.
     - If tests passed, the agent proceeds.
        Also incorporate one extra test call for a different feature: possibly the agent picks a random `passes=true` feature and re-runs its test as a “spot test”. Or we maintain a small set of core smoke tests to run always.
   - **Commit Phase Implementation**: Once satisfied, the agent calls a `commit` tool with a message. Our harness then performs `git add -A` and `git commit -m "<message>"`. The commit message is provided by the agent, but we can enforce a format (like include the feature ID or name).
   - **Update PRD**: The agent calls a `updatePRD(featureId)` tool or simply outputs a command to mark it done. We then programmatically set that feature’s `passes=true` in the JSON. Alternatively, we let the agent output the new JSON entry  and we merge it. Easiest: we do it outside the model once commit is done (since the agent knows it’s done, our code can just flip the flag and  save).
   - **Loop Control**: The agent (or the outer loop in `runCodingLoop()`) then checks time or PRD status to decide whether to continue with the  next feature or stop. Likely we handle time in outer loop for  reliability. We also handle if the agent indicates “I think I’m done”  (all features complete) – then exit.

   We will thoroughly test this by  possibly running the coding agent on a trivial feature to see that it  writes a file, passes a test, commits, and updates PRD.

5. **Integrate Testing & Linting in Workflow**: Ensure that the harness properly uses Playwright and ESLint at appropriate times:

   - Write a sample Playwright test (or test template) to verify the harness. For example, after initialization, we might run `npx playwright test --list` to ensure the config is fine.
   - Possibly create a dummy feature and manually test the `runTests` tool.
   - Make sure ESLint can be executed. We can add a script in `package.json` like `"lint": "eslint src --max-warnings=0"` and have the agent call that via shell.
   - The harness should be robust to  test failures (the agent should correct them). We might simulate a  failure in a controlled way to see if the agent reacts (this might be  done during development by temporarily altering a requirement).
   - Also, incorporate **progress logging**: after each feature, append to `progress.md` (with date/time and summary). We might implement a simple function to  do this rather than having the agent free-form write it, to keep format  consistent (the agent can supply the text, which we then append).

   Additionally, run **ESLint on the harness code** itself to ensure our implementation is clean. This is separate from the generated project’s lint, but we maintain both.

6. **Validation & End-to-End Testing**: Finally, test the entire harness on example project specs to validate that it behaves as expected:

   - Create a simple project spec (for example, a spec for a Hello World web app with two features) and run `bun run ralph.ts init spec.md`. Verify that it generates the PRD and scaffolds correctly, and that the Coding Agent loop starts.
   - Let the Coding Agent run for a  while. Observe that it picks features in order, creates code, runs  tests, and marks them done. The process should end with all features  passing.
   - Check the resulting repository:  all features should be implemented, tests should be present and green,  and the git log should show incremental commits with meaningful messages.
   - Test the restart capability: stop the agent mid-way (simulate an interruption or just use the time-budget logic by setting a low limit temporarily), then run `ralph.ts` again in continue mode. It should read the existing PRD and resume with the next feature seamlessly, proving that our persistence mechanism  works.
   - Try edge cases: a spec with no  features (should handle gracefully), a spec with a very large number of  features (performance), or features that are interdependent (the agent  should still do them one by one, and previous tests will catch if  something breaks).
   - Also ensure that if something  goes wrong (e.g. an exception in agent or tool), the harness doesn’t  leave the system in a bad state (maybe use transactions or temp branches for safety if needed, though probably not necessary).
